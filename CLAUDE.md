# FFE — guide pour Claude Code

Outil local, mono-utilisateur, de procurement FF&E (mobilier, luminaires, équipements d'aménagement intérieur ; résidentiel et hôtellerie).
Priorité : **fiabilité**, puis **simplicité**. Rien de clever : du code court, lisible, testé.
Langues : code (identifiants, fichiers, tables, colonnes, commentaires) en **anglais** ; UI, docs, ADR, JOURNAL et commits en **français**.
Avant toute tâche : lire `docs/ROADMAP.md` (où on en est) et `docs/JOURNAL.md` (dernière session).
Avant de toucher la base ou l'API : lire aussi `docs/DATA_MODEL.md` et `docs/ARCHITECTURE.md`. Les décisions tranchées sont dans `docs/decisions/` (ADR-0001 à 0021).

Les shells de Claude Code héritent de `UV_PROJECT_ENVIRONMENT=~/.venvs/racoon` et `UV_FROZEN=1` (réglage utilisateur, **non neutralisé** par le bloc `env` du projet, constaté le 2026-10-10) : tout `uv run` lancé tel quel **resynchronise le venv de Racoon sur le lock de FFE**. Donc : `check.sh` exporte lui-même les bonnes valeurs, et toute commande `uv` hors `check.sh` se lance avec `UV_PROJECT_ENVIRONMENT=/workspaces/Perso/FFE/api/.venv UV_FROZEN=0 uv …` (préfixe obligatoire). Si le venv de Racoon a été touché : `cd /workspaces/Perso/Racoon && UV_PROJECT_ENVIRONMENT=~/.venvs/racoon UV_FROZEN=1 uv sync` le restaure.

```

./check.sh contract                # régénère le contrat après un changement de route : ffe openapi puis npm run gen:api (ne vérifie rien)
cd api && uv run ffe serve [--reload]   # API FastAPI sur 127.0.0.1:8000 (uvicorn) ; sert web/dist/ si présent ; base de dev ~/.persist/ffe-dev (étape 3)
cd api && uv run pytest -q         # tests Python (base fichier temporaire migrée)
cd api && uv run ruff format --check . && uv run ruff check .   # format + lint (règles E9, F, I, UP)
cd api && uv run pyright           # typage strict
cd api && uv run alembic revision --autogenerate -m "<slug>"    # puis RELIRE alembic/versions/<rev>_<slug>.py ligne à ligne
cd api && uv run alembic upgrade head | check | history         # check = modèles et migrations coïncident (aussi lancé par pytest)
cd api && uv run ffe db migrate|backup [--with-files]|restore <f>|check [--files]|export-json [--with-files]|import-json <f>|seed [--demo]|import-contacts <csv>|reset-dev   # migrate = backup puis upgrade puis quick_check ; seed = 21 types de produit, --demo = projet d'exemple (une fois) ; import-contacts = annuaire CSV `;` (ADR-0015 ; colonnes facultatives SITE WEB, NOTES) ; reset-dev = base de dev recréée au schéma des modèles + seed + démo + annuaire (automatique au démarrage de `ffe serve` quand le schéma a changé ; jamais sur --prod)
cd api && uv run ffe openapi       # écrit api/openapi.json (commité) depuis create_app().openapi() (étape 1)
cd web && npm run dev              # Vite 5180 (strictPort ; pas 5173, réservé à d'autres projets), host:true (visible depuis Windows), proxy /api → 127.0.0.1:8000
cd web && npm run check            # tsc --noEmit && prettier --check . && vitest run — jamais vitest en mode watch
cd web && npm run gen:api          # scripts/gen-api.ts : ../api/openapi.json → src/api/schema.d.ts, sans API lancée (après `ffe openapi`)
cd web && npm run format | build   # prettier --write . | vite build
cd web && npm run e2e              # 2 parcours Playwright (étape 9) : API jetable sur 8001 + Vite 5181, données sous ~/.persist/.ffe-tests/e2e-* ; `npm run e2e:install` après un rebuild
```

Variables d'environnement : `FFE_DATA_DIR` (refusé si le FS n'est pas ext4), `FFE_BACKUP_DIR`, `FFE_DEV_CONTACTS_CSV` (dev) ; liste et défauts : ARCHITECTURE §1 (maître). Choix réel/dev (D3.4) : `FFE_ENV=dev` par défaut → `~/.persist/ffe-dev` ; `--prod` sur `ffe serve` et `ffe db …` → `~/.persist/ffe`.
Le dépôt est sur 9p (`/workspaces`) : jamais une base SQLite dedans ; `uv` avec `system-certs = true` (nouveau nom de `native-tls`) ; `vitest run` et `pytest` sans watch.

## Avant de committer

1. `./check.sh` vert, lancé depuis la racine. Pas de commit sur un check rouge ou « presque vert ». Un commit qui ne touche **que** `web/` peut se contenter de `./check.sh web` ; que `api/` de `./check.sh api` ; tout commit qui touche les deux, `api/openapi.json` ou `web/src/api/schema.d.ts` lance la porte complète.
2. Schéma modifié : **la v1 est déclarée (2026-10-14, ADR-0020)** : `0001_initial.py` est figée (empreinte testée) ; écrire une migration nouvelle `NNNN_<objet>.py` (`alembic revision --autogenerate -m …`), relue ligne à ligne, **additive seulement** (table, colonne nullable ou avec défaut, index ; données existantes remplies dans la même migration) ; jamais de suppression ni de renommage. `alembic check`, le rejeu sur base vide et `test_v1_upgrade.py` (base témoin v1 : aucune ligne perdue) passent. La base de dev se recrée seule au prochain `ffe serve` si son schéma diffère.
3. `docs/DATA_MODEL.md` mis à jour si une table change ; `docs/API.md` si une route change ; `docs/ROADMAP.md` coché si l'étape est finie ; `docs/JOURNAL.md` toujours.
4. Commit conventionnel en français, un par tâche : `feat|fix|refactor|docs|test|chore(scope): …` (scopes : `api`, `web`, `db`, `docs`, `repo`). Jamais `git push --force`, jamais `git add -A` sans relire `git status`.
5. Aucun fichier de données, `.env`, `*.sqlite*`, `node_modules`, `.venv` dans le commit (voir `.gitignore`).

## Tests

Ce qui est prouvé par couche, fichiers et étapes : ARCHITECTURE §7 (maître). Règles :

- Chaque test de base ouvre **son propre fichier temporaire migré** (`conftest.py`) ; **jamais la base réelle ni `~/.persist/ffe`** ; fixtures et seeds au format export JSON ; factories via les services, jamais en SQL direct ; pas de mock de SQLite.
- Toute nouvelle formule de `money.py` = cas de référence au centime écrit avant le code ; toute nouvelle contrainte = cas d'intégrité qui la fait lever.
- Nommage : `test_<module>.py` / `test_api_<resource>.py` côté Python (dont `test_openapi.py`, fraîcheur du contrat) ; côté front, `<Component>.test.tsx` à côté du composant, tests transverses (`schema-freshness.test.ts`, `boundaries.test.ts`) dans `web/tests/`. Un test = un comportement, nommé par le comportement attendu (`test_ordered_to_draft_is_refused`).
- `TestClient` sur `create_app(deps)` avec horloge injectée ; par ressource : 201 + relecture, PATCH partiel, 422 champ par champ, 404, 409, archive/désarchive.

## Règles dures

- **Pas de code pour plus tard** : aucune table, colonne, dossier, route, composant ou dépendance qui n'est pas utilisé et testé dans l'étape en cours ou dans l'étape suivante nommée dans `ROADMAP.md` (ex. tables de l'étape 3 servies par l'API de l'étape 4). Les accroches futures restent dans `docs/DATA_MODEL.md` §8 et `ROADMAP.md` (« Idées parquées »).
- **Un fait = un document maître** ; les autres le citent (`ARCHITECTURE §5`) sans le recopier. Maîtres : arborescence, variables d'environnement, cycle de démarrage, pragmas, sauvegardes, tests → `ARCHITECTURE.md` ; tables, statuts, formules, accroches futures → `DATA_MODEL.md` ; routes → `API.md` ; décisions → `docs/decisions/`.
- Une étape à la fois (`docs/ROADMAP.md`). Un besoin hors étape va dans « Idées parquées », pas dans le code.
- Données vivantes (base, WAL, fichiers joints, verrou) uniquement sous `FFE_DATA_DIR` sur **ext4** (`~/.persist/…`) ; refus de démarrer sinon (lecture de `/proc/mounts`) ; sur macOS, disque du Mac sous le dossier personnel, hors dossiers synchronisés (ADR-0019). Jamais `/workspaces`, `/mnt`, ni l'overlay. Copies de sauvegarde terminées : `FFE_BACKUP_DIR`.
- Cycle de démarrage, pragmas et sauvegardes : ARCHITECTURE §5 (maître). Règles dures : tout échec du cycle = arrêt sans servir, base intacte ; SQLite ≥ 3.37 ; jamais copier `ffe.sqlite` à chaud (`sqlite3.Connection.backup()` uniquement, puis `quick_check` du fichier produit).
- Migrations : **v1 déclarée le 2026-10-14 (ADR-0020) : `0001_initial.py` figée, une base réelle existe (Mac de l'utilisatrice)** ; chaque changement de schéma = une migration nouvelle, relue ligne à ligne, **additive seulement**, jamais éditée une fois publiée ; `tests/fixtures/v1_demo.sql` jamais régénérée ; démarrage arrêté si une migration fait perdre des lignes ; jamais d'autogénération non relue ; `alembic check` en test ; backup automatique avant chaque `upgrade`. Détail (batch, index d'expression, STRICT) : ARCHITECTURE §5.
- Argent : `*_cents INTEGER` HT + `currency` TEXT ISO 4217 ; taux en points de base `*_bp INTEGER` (10 000 = 100 %) ; quantités `qty_milli INTEGER` ; change `fx_rate_micro INTEGER` (1 unité = `fx_rate_micro`/1 000 000 EUR ; 1 000 000 pour l'EUR), figé par ligne. Jamais de REAL, jamais de float en Python pour un montant.
- **Tous les calculs dans `api/src/ffe/money.py`** (entiers, arrondi au centime à chaque étape de la formule). Rien de calculé n'est stocké ; **zéro vue SQL**, zéro somme en SQL ; le front n'additionne jamais, il affiche les DTO.
- Pas de marge ni de prix de vente en v1 (ADR-0005) ; multi-devises dès la v1 ; totaux et budgets en EUR net HT.
- Invariants dans la base : tables **STRICT**, `CHECK` (statuts, `≥ 0`, format SIREN 9 chiffres sur `client.siren`, `multiplier ≥ 1`), `UNIQUE` métier ; jamais de colonne nullable dans un `UNIQUE` sans `COALESCE` ou `WHERE` explicite. Tables au singulier, snake_case, `id INTEGER PRIMARY KEY` ; `*_at` ISO-8601 UTC posé par le service, `*_on` = `YYYY-MM-DD`.
- FK `ON DELETE RESTRICT` par défaut ; `CASCADE` seulement pour les enfants stricts (placements, événements, fichiers de jointure).
- Archiver (`archived_at`), ne pas supprimer. Suppression physique bornée : tout article avant le premier indice du projet, ensuite article « à chiffrer » sans événement (jamais une base qui a des options, ADR-0021), localisation vide, implantation (jamais la dernière), ligne de budget, fichier sans plus aucune jointure.
- Un article (`project_item`) porte sa fiche et son prix en copie **figée** (ADR-0013) ; tout changement de statut, de prix (coût, remise, devise, taux), de fiche, d'option ou d'implantation écrit `project_item_event` dans la même transaction. Codes sans trou (ADR-0021) : plus petit numéro libre ; avant le premier indice, un code libéré est comblé (les suivants descendent, journalisé), après, aucun code ne bouge ; `item_code_sequence` n'est plus utilisée.
- Statut unique d'un article : `to_quote · quoted · to_review · approved · deposit · purchased · cancelled`, changement libre (même statut → 409), journalisé, note facultative. `cancelled` non compté ; Devisé = rang ≥ `quoted`, Validé = rang ≥ `approved` ; `kind='fee'` (frais par fournisseur) compté dans le budget, sans type ni implantation, absent des fiches.
- Quantité totale d'un article = Σ (`qty_milli` de l'implantation × `multiplier` de la localisation) ; un code FF&E par **implantation** (`project_item_placement.code`, `<LOC>-<TYPE>-NN`, type = `category.code`, ADR-0018) : nouvelle implantation ou changement de localisation → nouveau code, changement de type → implantations recodées ; seuls les frais portent `project_item.item_code` (`FR-NN`) ; une **option** (`option_of_id`, `option_letter`, ADR-0021) reprend les implantations et les codes de sa base suivis de sa lettre (`CHA-LUD-01-A`), n'est comptée dans aucun total, se retient par échange des rôles ; `indice` déclaré sur le projet (« Nouvel indice », `POST /projects/{id}/indice`, 2026-10-13) : les articles modifiés depuis la déclaration précédente prennent la lettre (événement `indice`) ; `DELETE …/indice` retire la dernière déclaration (`project_indice`) ; un export ne marque jamais rien.
- Toute écriture passe par un service, dans une transaction (`with session.begin()`) ; les routeurs ne touchent jamais la session directement ; le module `db/` est le seul à parler à `sqlite3`/engine.
- API : préfixe `/api/v1`, JSON **camelCase** (alias Pydantic, aucun mapping manuel), erreurs typées `{code, message, details[{field, message}]}` ; 422 champ par champ, 404 cohérents, 409 avec `archivedId` sur doublon archivé ; jamais de 500 silencieux ; pas de pagination, sauf les deux listes du référentiel (`/suppliers`, `/professionals` : `?q=&limit=50&offset=0`, `limit` jusqu'à 1000, réponse `{items, total}`, cf. `docs/API.md` §Listes).
- Serveur à l'écoute de **`127.0.0.1:8000` seulement** ; Vite proxifie `/api`. Le front n'appelle **jamais** un service externe ; toute intégration passe par le back, et le seul accès réseau sortant est `Deps.fetch_url` (ADR-0014 : une page à la demande, jamais de parcours de site).
- Front : TypeScript strict, pas d'`enum`, pas de `any` ; types API uniquement depuis `src/api/schema.d.ts` généré (jamais de type API écrit à la main) ; `schema.d.ts` régénéré et commité à chaque changement de route.
- Messages serveur (erreurs, libellés d'enums) dans `api/src/ffe/i18n/fr.py`, jamais en dur dans un routeur ou un service. Côté front, application mono-langue : textes français écrits dans les composants (ROADMAP D5.4), pas de couche i18n.
- Pas de nouvelle dépendance (`uv add`, `npm install`) sans ligne dans l'ADR concerné ; question de conception → ADR (≤ 25 lignes, gabarit `docs/decisions/README.md`) avant le code.
- Dirigeants d'entreprise : jamais stockés. Pas de scraping ni de copie de catalogues, ni de capture en masse : import des tarifs fournis, « coller une URL » et extension à la demande seulement (plan validé le 2026-10-09 ; ROADMAP F4–F6).

## Réutiliser d'abord

`money.py` pour tout calcul (jamais une multiplication locale) ; `services/project_item.change_status` pour tout changement de statut ; `schemas/` Pydantic existants avant tout nouveau type ; `services/<table>.py` pour toute écriture (journal garanti), `services/project_item.py` pour tout article ; `ffe/errors.py` pour toute erreur ; `db/json_io.py` pour tout import/export ; `tests/conftest.py` et ses factories pour tout test ; côté front `components/forms/*` pour tout champ, `components/tables/TableCard` + `ListToolbar` (sur `DataTable`) pour toute liste, `api/queries/<table>.ts` pour tout appel. Vérifier l'existant (`grep`) avant de créer un module.

## Collaboration

- **Phase de conception (depuis le 2026-10-13)** : l'utilisateur dessine l'application par retouches rapides ; chaque retouche = modification + au plus une vérification ciblée (fichier de test, `tsc`), **sans porte complète ni commit**. Porte complète, commits, régénération de la base de dev : **à sa demande seulement**, groupés. La consolidation (tests par ressource, docs maîtres, ADR) se fera item par item une fois la conception validée. Les règles « Avant de committer » restent entières au moment du commit.
- **Une étape à la fois**, dans l'ordre de `docs/ROADMAP.md`. Une étape = une session courte : fichiers + `./check.sh` vert + commit(s) conventionnel(s) + compte rendu.
- **Début d'étape** : relire `ROADMAP.md` et `JOURNAL.md` ; poser **toutes** les décisions de l'étape en **un seul bloc numéroté** (question, recommandation, défaut) ; attendre la réponse. « défaut » ou silence = défaut appliqué, noté comme tel dans `JOURNAL.md`.
- **Fin d'étape** : compte rendu ≤ 10 lignes (fait / décisions prises / commits / 3 vérifications que l'utilisateur peut faire en 5 min / reste ou parqué), copié tel quel dans `docs/JOURNAL.md` ; `ROADMAP.md` coché avec la date et le commit.
- **Ne jamais redemander une décision tranchée** : citer l'ADR (`ADR-0003 §Décision`) ou le paragraphe du JOURNAL. Une décision à revoir = nouvelle ADR qui remplace l'ancienne, pas une discussion.
- Ne jamais inventer un fait technique ; si un détail manque, l'écrire « à trancher à l'étape N » et le mettre dans le bloc de décisions de cette étape.
- Scripts jetables, essais, exports de debug : dans le scratchpad de la session, **jamais dans le dépôt**. Captures d'écran et essais navigateur : seulement si l'utilisateur les demande.
- Pas de CI, pas de hooks git : `./check.sh` est la seule porte. Pas de refactor opportuniste hors du périmètre de l'étape.
- S'adresser à l'utilisateur en français, sobrement ; dans les docs, style impersonnel.
